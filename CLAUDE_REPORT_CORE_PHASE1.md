## 2. Архитектура

### 2.1 Модули и направление зависимостей

```
WmsConfig ◄── все модули (константы, раскладка _SYS)
WmsCore   ── общее состояние, _SYS, события, ApplyOperation, план, Undo, разбор количества
   │  вызывает
   ├─► WmsRecovery.Analyze      (запуск)       ──► WmsLock, WmsJournal, WmsBackup, WmsDiagnostics
   ├─► WmsJournal.AppendLine    (точка фиксации)
   └─► WmsLock.VerifyOwner      (перед каждым проведением)
Операции этапа 2 (и WmsTestOps сейчас): фаза 1 (проверки, без изменений) → Plan* → WmsCore.ApplyOperation
```

События книги привязывает `tools/build_ods.py`:

| Событие | Обработчик | Что делает |
|---|---|---|
| OnLoad | `WmsCore.OnDocLoad` | Запуск и анализ |
| OnSave | `WmsCore.OnDocSave` | Метка сохранения |
| OnPrepareUnload | `WmsCore.OnDocPrepareUnload` | Снятие своей блокировки, возврат AutoInput |

Страховка на случай, если событие открытия не сработало: любое проведение само сначала выполняет запуск и только потом пишет (T32).

### 2.2 `_SYS` (скрытый защищённый лист; структура документа защищена)

Столбец A — ключ, столбец B — значение. Номер строки фиксирован (`SK_*`).
При каждом запуске проверяются:
- раскладка (ключи на своих местах);
- схема;
- `INSTANCE_ID`;
- числовые поля.

Любое расхождение даёт блок `SYS_CORRUPT` (T32).

| Ключ | Назначение (п. 2 задания) |
|---|---|
| `SCHEMA`, `CORE_VERSION` | schema/version (`WMS-SYS-1`, `0.1.0-phase1`) |
| `INSTANCE_ID` | Идентификатор экземпляра WMS: 16 hex-символов, создаются при сборке. Есть в каждой строке журнала |
| `MODE` | `PROD` или `TEST`. Тестовый шов работает только в `TEST` |
| `LAST_SEQ` | Последняя операция, применённая в книге |
| `NEXT_EI`, `NEXT_NO`, `NEXT_RET` | Счётчики ключей. Этап 1 их только хранит и проверяет; тестовая операция расходует `NEXT_NO` |
| `JOURNAL_POS` | Позиция журнала в формате `файл\|смещение в байтах\|seq` |
| `REGISTERED_URL` | Зарегистрированный рабочий путь книги |
| `TX_STATE`, `TX_SEQ`, `TX_TYPE`, `TX_TIME`, `TX_BEFORE_IMAGE` | Маркер текущей операции (`NONE` / `STARTED` / `COMMITTED`) и печатный снимок до изменения |
| `SAVE_STAMP`, `SAVE_SEQ` | Метка последнего сохранения средствами WMS (last clean save marker) |
| `MAX_QTY` | Второй защитный порог количества (§12) |
| `KEY_SHEETS` | Листы с ключами для полной проверки: `лист\|колонка ключа\|колонка контроля\|строка счётчика\|колонка ввода` |

### 2.3 Единственный путь записи: план и `ApplyOperation` (§18, D-027)

**Фаза 1 — модуль операции.** Модуль проверяет, нормализует и рассчитывает, ничего не меняя в документе. Затем описывает все изменения планом:
- `PlanSetValue(лист, строка, колонка, значение, restorable)` — запись значения. Тип `V` хранит «до» и «после».
- `PlanInput(лист, строка, колонка)` — пользовательский ввод, на который опирается операция. Тип `I`.
- `PlanLock(лист, строка, c1, c2, заблокировать)` — защита ячеек. Тип `L`.
- `PlanField(имя, значение)` — логические поля записи журнала (для аудита).

Операции только пишут ячейки и биты защиты. Строки они не вставляют и не удаляют.

**Фаза 2 — `WmsCore.ApplyOperation(mode, replaySeq)`:**
1. Проверки. `mode 0`: запуск завершён чисто, другая операция сейчас не выполняется (защита от повторного входа), блокировка всё ещё наша. `mode 1` (повтор при восстановлении) разрешён только в состоянии `RECOVERING`.
2. Undo блокируется.
3. **STARTED + снимок до изменения.** Снимок — это текущие значения и биты защиты всех ячеек плана, только печатными символами.
4. **Изменения** по плану.
5. **Точка фиксации:** строка журнала `WmsJournal.AppendLine`. Результат дозаписи:
   - `1` — записано;
   - `0` — не записано → полный откат по снимку;
   - `2` — неизвестно → блок `JOURNAL_UNCERTAIN`. Маркер остаётся `STARTED`, решает следующий запуск (откат по снимку, затем журнал).
6. **COMMITTED + LAST_SEQ.** Порядок записи важен: сначала `TX_STATE = COMMITTED`, затем `LAST_SEQ`, `TX_SEQ` и очистка снимка. Если завершение оборвётся на любом шаге (ошибка, сохранение, авария), `LAST_SEQ` никогда не окажется впереди маркера `STARTED`. Затем Undo разблокируется, стек очищается.

Ошибки:
- **До строки журнала** — полный откат по снимку и очистка маркера. Если откат не удался — блок `ROLLBACK_FAILED` (T04, T05, T36).
- **После строки журнала** — операция не откатывается, а доводится (T06).
- **Довести не удалось, повтор тоже упал** — блок `COMMIT_FAILED`. Стек Undo очищается: Ctrl+Z не может отменить записи WMS. Проведение запрещено до перезапуска. Книгу можно сохранить или не сохранять. Следующий запуск либо откатит по маркеру и повторит операцию из журнала, либо увидит, что она уже в книге. В обоих случаях операция окажется в книге ровно один раз (T38).

**Повтор (replay) не содержит кода конкретных операций.** Строка журнала несёт записи изменений `W=вид|лист|строка|колонка|до|после|restorable`. Перед повтором каждая операция классифицируется по текущему состоянию книги:
- `APPLY` — книга в состоянии «до». Пропавший ввод (`I`) восстанавливается из журнала.
- `ALREADY` — все изменения уже в книге. Двойного применения нет.
- `CONFLICT` — книга отличается и от «до», и от «после», или операция присутствует частично. Восстановление останавливается на этой операции для ручного решения.

Этапу 2 не нужно писать отдельный код восстановления для выдачи, прихода или возврата.

### 2.4 Внешний журнал (§20, D-029)

- **Папка и файлы.** Журнал лежит в `WMS_Journal/` рядом с книгой. Один файл на месяц: `WMS_journal_YYYY-MM.csv`.
- **Строка:** `J1;seq;время;экземпляр;тип;поля...;END;длина`. Длина — число символов до `;END;`.
- **Кодировка и запись:** UTF-8, LF, только дозапись.
- **Экранирование.** В значениях полей экранируются `% ; | = ~` и управляющие символы (`%XX`). Строка всегда печатная и однострочная (T33).
- **Служебные записи:**
  - `ABANDON` (`FROM`, `TO`) — отложенный хвост;
  - `START` (`BASE`) — новый журнал после переноса книги без журнала.

**Дозапись (`AppendLine`):**
- **Проверка владения.** Размер файла должен быть ровно таким, каким его оставил этот сеанс. Если размер другой, значит файл дописал посторонний: `JOURNAL_FOREIGN_WRITE`, операция откатывается, проведение остановлено (T16).
- **Оборванная прошлая строка.** Если в конце файла нет LF, перед новой строкой пишется LF. Оборванная строка закрывается, но никогда не продолжается.
- **Сбой посреди записи.** Хвост файла перечитывается:
  - строка целиком → операция зафиксирована;
  - строка целиком, но без LF → тоже зафиксирована, её примет любой читатель;
  - только часть строки → операции нет, откат;
  - чужие байты → «неизвестно», блок.

  Первые три случая проверяет T36.
- **Имена файлов не идут назад.** Дозапись никогда не идёт в файл, имя которого сортируется раньше уже используемого. Если часы компьютера отстают (например, сбросилась батарейка BIOS), записи продолжаются в последнем файле, а отчёт запуска предупреждает (T37). Иначе порядок seq в файлах нарушился бы.
- **После записи** обновляется `JOURNAL_POS`.

**Чтение (`ReadJournal`)** выбирает самый дешёвый безопасный способ:
1. **Позиция подтверждена содержимым:** в файле строка, заканчивающаяся ровно на смещении, начинается с `J1;<LAST_SEQ>;`. Тогда читается только то, что после неё (T35: 20–27 мс при 60 000 записей).
2. **Позиция не подтвердилась** (файл перекодирован CRLF↔LF, обрезан, правлен; неверное смещение или seq). Тогда перечитываются файл позиции и следующие файлы. Результат принимается, только если там есть последняя операция книги и seq непрерывен (T12–T14; T35: около 0,85–1,1 с на месяц в 5 000 записей).
3. **Иначе** читается весь журнал (T14, T35).

Проверяется:
- непрерывность seq;
- строки чужого экземпляра;
- повреждённые строки;
- оборванная последняя строка;
- начало истории — позже 1 допускается только с `START`.

После «Восстановить» позиция переставляется на последнюю применённую запись. Следующий запуск снова идёт по быстрому пути (T10).

### 2.5 Запуск (fail-closed, §21, D-028)

`WmsRecovery.Analyze` проверяет по порядку и останавливается на первой проблеме. Проведение разрешено только в состоянии `CLEAN`. Любая неожиданная ошибка запуска даёт `STARTUP_ERROR`.

| # | Проверка | Блок | Тест |
|---|---|---|---|
| 1 | Книга сохранена в файл; не только для чтения; формат ODS (фильтр `calc8` и расширение `.ods`) | `NO_FILE`, `READ_ONLY`, `NOT_ODS` | T27 |
| 2 | Раскладка и значения `_SYS` | `SYS_CORRUPT` | T32 |
| 3 | Рабочий путь. Копия или старая резервная копия, открытая напрямую, не трогает ни блокировку, ни журнал, ни копии | `NOT_REGISTERED` | T20, T22 |
| 4 | Блокировка WMS: устаревшая после аварии или второй экземпляр | `LOCKED` | T18, T19 |
| 5 | (Сеанс владеет WMS) ежедневная копия; AutoInput выключен | — | T01, T29, T30 |
| 6 | Маркер: `STARTED` → откат по снимку. Повреждённый снимок, неизвестное состояние или `STARTED` не для операции `LAST_SEQ + 1` → блок. `COMMITTED`, после которого остался снимок (прерванное завершение), приводится в порядок | `MARKER_CORRUPT` | T07, T08, T23, T38 |
| 7 | Журнал: не читается / чужой экземпляр / разрыв seq / книга впереди журнала / хвост операций вне книги | `JOURNAL_UNREADABLE`, `JOURNAL_FOREIGN`, `JOURNAL_GAP`, `JOURNAL_BEHIND`, `TAIL` | T08–T17, T21 |
| 8 | Метка сохранения. Книга сохранялась без WMS (макросы отключены, ошибка компиляции, другая программа) → полная проверка ключей порциями. Невыданные или повторные ключи помечаются «КОПИЯ» и не проводятся | `SAVED_WITHOUT_WMS` (если проверка сама не удалась) | T24 |

Состояния, которые могут возникнуть во время работы и останавливают проведение до перезапуска или явного действия:

| Состояние | Когда |
|---|---|
| `LOCK_LOST` | Блокировку сняли или захватили другим экземпляром |
| `JOURNAL_FOREIGN_WRITE` | Журнал дописан посторонним |
| `JOURNAL_UNCERTAIN` | Неизвестно, записалась ли строка журнала |
| `ROLLBACK_FAILED` | Откат по снимку не удался |
| `COMMIT_FAILED` | Операция в журнале, но не завершена в книге |

**Ни одна учётная операция не проходит молча после ошибки запуска.** Все проведения идут через `PostingBlockReason` и получают `BLOCKED:<причина>`. Проверено в T10, T15–T20, T23, T27, T32 (таблица 3.2).

### 2.6 Явные действия (§21)

| Действие | Функция | Что делает |
|---|---|---|
| Восстановить | `WmsCore.ActionRecover` | Только при блоке `TAIL`. Перечитывает и перепроверяет хвост. Применяет строго по seq через `ApplyOperation(mode 1)` с классификацией APPLY/ALREADY/CONFLICT. Останавливается на первой проблеме. Затем повторяет запуск |
| Отложить хвост журнала | `ActionAbandonTail` | Только при `TAIL`. Дописывает `ABANDON FROM..TO` (журнал остаётся только-дозапись). Книга продолжает после него. Отложенные операции остаются в журнале для ручной сверки (T11) |
| Снять блокировку WMS | `ActionForceUnlock` | Пользователь подтверждает, что другой WMS нет. Lock-файл удаляется, запуск повторяется. Экземпляр, у которого блокировку отняли, останавливается (T18, T19) |
| Сделать рабочим файлом | `ActionRegisterHere(новый журнал?)` | Регистрирует текущий путь. Если в папке нет журнала и попросили начать новый — дописывает `START BASE=<LAST_SEQ>` (T22) |
| Ручная копия | `ActionBackupNow` | Копия последнего сохранённого файла |
| Самопроверка | `ActionSelfCheck` | Раздел 2.10 |
| Отчёт запуска | `StartupReport` | Состояние, причина блока и заметки запуска |

### 2.7 Блокировка WMS и рабочий путь (§22)

**Блокировка:**
- Файл `WMS_Journal/wms.lock`: `WMSLOCK1;session=…;instance=…;opened=…;user=…;host=…;`.
- Создаётся при запуске и перечитывается для проверки: при одновременном старте побеждает последний записавший.
- Перед каждым проведением проверяется, что блокировка всё ещё существует и принадлежит этому сеансу.
- При закрытии окна снимается только владельцем.
- После аварии снимается только явным действием.

**Рабочий путь.** Книга без единой операции (`LAST_SEQ = 0`) регистрирует себя при первом запуске. Внутри `WMS_Backups/` она не регистрируется никогда: резервная копия, открытая там, остаётся копией. Во всех остальных случаях путь должен совпасть с `REGISTERED_URL`, иначе нужно явное «Сделать рабочим файлом».

### 2.8 Резервные копии (§26)

- **Где и как называются:** `WMS_Backups/<книга>_YYYY-MM-DD_HHMMSS_<вид>.ods`.
- **Что это:** копия файла на диске, то есть последнего сохранённого состояния.
- **Виды и сколько хранится:**

| Вид | Когда | Хранится |
|---|---|---:|
| `daily` | Один раз в день, первым владельцем блокировки | 14 |
| `manual` | Вручную | 10 |
| `preupgrade` | Перед обновлением, `WmsBackup.BeforeUpgrade` — точка подключения для будущей функции обновления | 5 |
| `premigration` | Перед миграцией, `BeforeMigration` — точка подключения для будущей функции миграции | 5 |

- **Ротация** по каждому виду отдельно; другие виды не трогаются (T30).
- **Копия не заменяет журнал.** Чтобы вернуться к копии, её копируют на место рабочей книги и выполняют «Восстановить»: журнал доводит книгу до актуального состояния (T21).

### 2.9 Undo (§17)

`ApplyOperation` блокирует менеджер Undo на время операции. Но Calc сам снимает эту блокировку посреди операции: изменение защиты листа и атрибутов ячеек снова включает Undo. Это найдено тестом T38 (раздел 3.6). Поэтому гарантия держится на очистке стека в конце — на всех путях:
- после операции, отката и любого блока, включая `COMMIT_FAILED`;
- после повтора операций при «Восстановить»;
- после анализа при запуске и после явных действий. Запуск откатывает незавершённую операцию, регистрирует путь, помечает копии — ничего из этого нельзя отменить Ctrl+Z.

Исключение — только имитация аварии в тестовом шве: там процесс сразу убивается.

Результат (T25, T38):
- после проведения, после сбоя завершения, после запуска и после «Восстановить» пять Ctrl+Z ничего не меняют в строках, защите ячеек и `_SYS`;
- Undo не остаётся заблокированным;
- обычный ручной ввод записывается в Undo и отменяется Ctrl+Z как обычно.

### 2.10 Самопроверка (§49, минимальная)

`WmsDiagnostics.SelfCheck` выводит строки `OK/WARN/FAIL`:
- формат ODS;
- `_SYS`;
- счётчики;
- маркер и снимок;
- рабочий путь;
- владение блокировкой;
- журнал — полное чтение, непрерывность, чужие и повреждённые строки, операции вне книги;
- подтверждение позиции журнала;
- сеанс WMS;
- метка сохранения;
- AutoInput;
- ключи — полная проверка порциями.

Базу владения журналом самопроверка не сдвигает: чужая запись остаётся обнаружимой и для следующей дозаписи. T31 проверяет, что самопроверка сообщает о чужой строке журнала.

### 2.11 Разбор количества без зависимости от локали (§12, D-030)

`WmsCore.ParseQtyText` и `ParseQtyCell` возвращают канонический Double (не больше 3 знаков) и статус:

| Статус | Значение |
|---:|---|
| 0 | Норма |
| 1 | Пусто |
| 2 | Недопустимо |
| 3 | Неоднозначно |
| 4 | Больше 3 знаков |
| 5 | Не больше нуля |
| 6 | Похоже на дату |

- **Принимается:** `1,5`, `1.5`, `0,125`, `10,75`, `1,50`, `1000,5`.
- **Неоднозначно:** ровно 3 цифры после разделителя при 1–3 цифрах до него (`1,500`, `12.345`). Сообщение подсказывает однозначную форму: `1,5`, `1500` или четвёртый ноль `2,1250` = 2,125.
- **Отвергается:**
  - даты;
  - несколько разделителей;
  - экспонента;
  - минус (в том числе U+2212);
  - пробелы внутри числа, включая неразрывный;
  - дроби и знаки автозамены `1/2`, `½`;
  - ведущие нули;
  - `,5` и `1,`;
  - больше 9 цифр целой части;
  - буквы.
- **Ячейка-число**, которую Calc распознал как дату, время, процент или дробь, отвергается. Защитный порог — `MAX_QTY`.

T28 проверяет 34 варианта. Ввод с клавиатуры в текстовые ячейки даёт одинаковый результат в ru-RU и en-US: `1,500` не становится 1500.

### 2.12 AutoInput (§10, §29, D-031)

- При запуске исходное значение запоминается в файле профиля LibreOffice `<UserConfig>/wms_autoinput.state`. Только один раз: после аварии там остаётся исходное.
- Затем автоввод выключается.
- При чистом закрытии значение восстанавливается, файл удаляется (T29).
- **Настройка общая для профиля LibreOffice.** Пока WMS открыта, автоввод выключен во всех книгах Calc этого пользователя. Об этом сказано в отчёте запуска и в `WmsConfig.bas`.

### 2.13 «Сохранено без WMS» и правило копии (§15, §24, §30, D-032, D-034)

**Метка сохранения.** `OnDocSave` записывает `SAVE_STAMP` = номер редакции документа (`EditingCycles`) после этого сохранения. Если при запуске метка не совпала, книга сохранялась без WMS.

**Полная проверка ключей** (`FullKeyCheck`):
- идёт по листам из `KEY_SHEETS`, только по нужным колонкам, порциями по 20 000 строк;
- повторы ищутся сортировкой Calc (C++) в служебной области `_SYS`, а не циклом Basic;
- ключ, который WMS не выдавала (`≥ счётчика`), повторный или неверный, помечается `КОПИЯ` и не проводится.

T24: при отключённых макросах подделан ключ 99 и скопирован ключ 1. Обе строки при следующем запуске помечены.

### 2.14 Сборка и тестовый шов

`python3 tools/build_ods.py OUT.ods [--test]` собирает книгу из текстовых модулей:
- `_SYS`;
- 7 модулей;
- привязка событий;
- защита `_SYS` и структуры документа;
- метка сохранения, проверяется повторным открытием.

С флагом `--test` добавляются `WmsTestOps` и лист `_TST`, `MODE=TEST`.

**Тестовый шов** `TestSetFault(точка, режим)` работает только в `MODE=TEST`: в production-книге он отвечает `REFUSED` (T34). Точки:
- 1 — после STARTED;
- 2 — посреди изменений;
- 3 — после журнала;
- 4 и 5 — внутри дозаписи (половина строки / всё без LF);
- 6, 7, 8 — внутри завершения `CommitSeq` (до записей / после `COMMITTED` / после `LAST_SEQ`).

Режимы:
- 1 — ошибка;
- 2 — книга сохраняется в момент сбоя, имитируется авария; процесс затем убивается `kill -9`;
- 3 — ошибка, которая остаётся взведённой: повторная попытка падает тоже.

### 2.15 Как на это опирается этап 2

Операция «Выдачи» — это модуль по образцу `WmsTestOps.TestPost`:
1. Фаза 1: проверки, нормализация ЕИ, количество через `ParseQtyCell`, расчёт остатка.
2. План: `PlanField` (ЕИ, количество, остатки до и после), `PlanInput` для ввода, `PlanSetValue` для № / остатков / статуса / счётчиков, `PlanLock`.
3. `ApplyOperation(0, 0)`.

Журнал, откат, восстановление, блокировки, копии и самопроверка уже работают для любого такого плана. Лист «Выдачи» нужно добавить в `KEY_SHEETS`.

### 3.5 Дефекты, найденные на этом этапе (все исправлены)

1. **Однострочный `If … Then ReDim Preserve …` проглатывает следующую строку.** LibreOffice Basic считает её частью `If`. Поля журнала оказывались пустыми (`NO=;TEXT=`), это поймал оракул в T02. Исправлено блочным `If`. Правило для этапа 2 — в разделе 7.
2. **`clearContents` молча не выполняется для заблокированной ячейки защищённого листа.** Откат значения «пусто» ничего не делал, это поймал T04. `ClearCell` снимает защиту листа на время очистки и проверяет результат.
3. **`setString("")` не очищает ячейку.** Служебные значения очищаются через `ClearCell`.
4. **Нетронутая ежедневная копия, открытая из `WMS_Backups`, регистрировала себя рабочей книгой.** Первая сессия, убитая до сохранения, давала ложный `NOT_REGISTERED`. Исправлено правилами регистрации (2.7).
5. **Часы компьютера отставали от последнего файла журнала.** Новые записи уходили в файл, который сортируется раньше: при следующем запуске ложный разрыв seq, при быстром пути — риск не увидеть хвост. Исправлено (2.4), тест T37.
6. **Сбой посреди дозаписи различался грубо.** «Вся строка без LF» считалась незаписанной, хотя любой читатель её примет: следующая операция получила бы тот же seq. Чужие байты «узаконивались». Исправлено (2.4), тест T36.
7. **После «Восстановить» позиция журнала оставалась старой.** Следующий запуск шёл медленным путём и писал ложное «позиция не подтвердилась». Исправлено, тест T10.
8. **`COMMIT_FAILED` оставлял записи WMS в стеке Undo.** Найдено ревью кода, доказано тестом T38. Ctrl+Z после сбоя мог отменить записи WMS; в проверке он снял защиту проведённой строки (`1111` → `1000`). Первоначальное описание «Undo остаётся заблокированным» оказалось неточным: блокировку снимает сам Calc (2.9), а опасен неочищенный стек. Исправлено: на этом пути стек тоже очищается.
9. **Записи анализа при запуске оставались в стеке Undo.** Найдено при разработке T38. После отката незавершённой операции по маркеру восемь Ctrl+Z возвращали ячейку в состояние «проведено», а маркер — в `STARTED`. Исправлено: стек очищается после каждого анализа запуска (2.9).
10. **Порядок записи при завершении.** Найдено при разработке T38. `CommitSeq` писал `LAST_SEQ` раньше `COMMITTED`. Если завершение обрывалось между ними, а книгу сохраняли, следующий запуск откатывал ячейки и всё равно считал операцию применённой. Это тихая потеря операции и повтор номера. Исправлено тремя мерами:
    - новый порядок записи (2.3);
    - проверка маркера при запуске (2.5; вариант добавлен в T23);
    - приведение в порядок `COMMITTED` с оставшимся снимком.

### 3.6 Регрессионный тест T38 — сбой завершения после точки фиксации

Для сбоя в тестовом шве добавлены точки 6/7/8 внутри завершения `CommitSeq` и режим 3 — ошибка, которая повторяется при повторной попытке (2.14). Сценарии:

| Вариант | Что происходит |
|---|---|
| A6, A7 | Операция №2 записана в журнал. Завершение в книге падает (точка 6 — до записей, 7 — после `COMMITTED`) и падает снова при повторе → `COMMIT_FAILED`. Книгу **сохраняют**, перезапуск, «Восстановить» |
| B6 | То же, но книгу **не сохраняют** |
| C6, C7, C8 | Книга сохраняется посреди завершения (точки 6/7/8), процесс убит `kill -9`; перезапуск, «Снять блокировку WMS», при хвосте — «Восстановить» |

| Пункт задания | Проверка в T38 |
|---|---|
| 1. Операция дошла до journal commit point | До сбоя записи №2 в журнале нет, после сбоя она есть (seq 2) |
| 2. Искусственная ошибка при завершении в книге | Результат `ERR-CRITICAL`, блок `COMMIT_FAILED`, `LAST_SEQ` не сдвинут, следующее проведение — `BLOCKED` |
| 3. Recovery приводит состояние к корректному | Перезапуск: откат по маркеру (A6, B6, C6) или «уже в книге» (A7, C7); «Восстановить» → `CLEAN`, `LAST_SEQ` = 2. C8 — чисто сразу после запуска |

## 4. Известные ограничения

1. **Проверено только на LibreOffice 24.2.7 в Linux-контейнере.** Не проверено на складском Ubuntu-ПК и на Windows-ПК разработчика. Это обязательно до миграции (D-036). Замеры (раздел 5) — облачные.
2. **Пользовательского интерфейса нет, это следующий слой.** Состояние запуска и действия — функции Basic из раздела 2.6; сейчас их можно вызвать через «Сервис → Макросы». При открытии книги окно не показывается: заблокированная WMS видна в `StartupReport` и в ответе `BLOCKED:…` на любую попытку проведения. Кнопки и строку состояния разумно сделать в начале этапа 2 вместе с листом «Выдачи».
3. **Запуск проверяет журнал от подтверждённой позиции (§20).** Повреждение старой истории запуск не видит: например, удалённую строку в прошлом месяце. Всю историю читает только самопроверка (T31). Если правка задела файл позиции, позиция не подтверждается, запуск перечитывает файл и находит разрыв (T15). Рекомендуется регулярная самопроверка, например раз в неделю и перед копированием на внешний носитель.
4. **Полное чтение журнала линейно: около 0,15–0,18 мс на запись** (60 000 → 9–11 с). Оно нужно только когда позиция не подтвердилась и файл позиции не помог, и в самопроверке. Для многолетнего журнала позже понадобится контрольная точка или архив старых месяцев. Это не этап 1.
5. **Длина строки журнала.** Проверка позиции читает не больше 4 КБ (`JPOS_VERIFY_WINDOW`). Строку длиннее 4 КБ позиция никогда не подтвердит, и каждый запуск будет перечитывать файл. Это медленнее, но корректно. Операции этапа 2 должны укладываться в 4 КБ на строку (тестовая — около 260 байт) либо увеличить окно.
6. **Нет принудительного сброса на диск (fsync).** Файловый API LibreOffice его не даёт.
   - Авария процесса (`kill -9`) данных не теряет — проверено.
   - При пропадании питания ОС может не успеть записать последние строки журнала. Если книга после них была сохранена и её запись дошла до диска, следующий запуск даст `JOURNAL_BEHIND` (fail-closed). Выход — ручной: сверка, затем «Сделать рабочим файлом» с новым журналом.
   - Рекомендация к пилоту: ИБП на складской ПК.
7. **Блокировка рекомендательная, файл создаётся не атомарно.** В SimpleFileAccess нет эксклюзивного создания. Защита держится на трёх проверках:
   - запись + перечитывание;
   - проверка владения перед каждым проведением;
   - проверка размера журнала перед каждой дозаписью.

   Только локальный диск. Сетевой диск и многопользовательский режим — вне ядра (§34).
8. **«Восстановить» требует, чтобы ячейки книги были в состоянии «до».** Любое отличие (`CONFLICT`) останавливает восстановление для ручного решения — так задумано. Отложенные операции (ABANDON) остаются в журнале; инструмента сверки пока нет.
9. **Признак «сохранено без WMS» — номер редакции `EditingCycles`.** Программа, которая меняет содержимое, но сохраняет тот же номер редакции, не будет замечена; это маловероятно. Полная проверка ключей охватывает только листы из `KEY_SHEETS`, сейчас только `_TST`. Этап 2 должен зарегистрировать «Выдачи».
10. **Команда «Очистить копию»** (§15, упоминается в пометке «КОПИЯ») зависит от раскладки бизнес-листа. Это этап 2.
11. **AutoInput — общая настройка профиля LibreOffice** (2.12). После `kill -9` LibreOffice сам не сохраняет изменённое значение: при следующем запуске LibreOffice автоввод уже исходный (T29).
12. **Пароль защиты — константа в исходнике.** Защита от случайностей, а не от злоумышленника (§16).
13. **Ошибка компиляции любого модуля отключает всю библиотеку.** Тогда код WMS не выполняется вовсе, и проведение невозможно. Сохранение в этом состоянии обнаруживает метка сохранения (§30). Перед каждым выпуском обязателен `tools/basic_compile_check.py`.
14. **Время строк журнала и имена копий берутся из часов компьютера.** Отстающие часы не ломают порядок журнала (T37), но время в записях будет неверным, а отчёт запуска предупредит.
15. **Оракул тестов знает только тестовую операцию.** Инварианты «Выдач» (остатки, отсутствие двойных движений) добавляются в оракул в этапе 2.
16. **Undo: две записи WMS остаются отменяемыми, обе безвредны.**
    - Метка сохранения, которую пишет `OnDocSave`: после Ctrl+S её можно отменить Ctrl+Z, но при следующем сохранении она пишется заново.
    - Служебная область сортировки в `_SYS`, которую использует самопроверка.

    Учётные данные, маркер, счётчики и пометки «КОПИЯ» Ctrl+Z не отменяются (2.9).

## 7. Особенности LibreOffice Basic, найденные на этапе (обязательны для этапа 2)

1. **`Dim` — только в начале процедуры.** Никаких однострочных `If … Then ReDim …`: следующая строка становится частью `If`. Нужен блочный `If … End If`.
2. **`Err.Raise` / `Error n` не использовать.** Ошибки передаются возвращаемыми значениями, как в `DecToCell` и `ApplyWrites`.
3. **Очистка ячеек.**
   - `setString("")` и `setFormula("")` ячейку не очищают.
   - `clearContents` на заблокированной ячейке защищённого листа в Basic молча не выполняется, в Python — исключение.
   - Только `ClearCell`.
4. **`setDataArray` на защищённом листе выбрасывает исключение.** Операции пишут точечно.
5. **Недоступны `AscW`, `ChrW`, `InStrRev`.** Использовать `Asc`/`Chr` (Unicode) и свои циклы.
6. **`Environ("USER")` может быть пустым** (так было в контейнере). В блокировке имя пользователя и хоста — только справка.
7. **Печатные служебные данные.** Любые служебные разделители — только печатные символы (§19). `Esc`/`Unesc` уже есть.
