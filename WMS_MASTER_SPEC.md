# WMS MASTER SPEC v0.1

Дата: 24.09.2026

Статус: проект спецификации для утверждения

Приоритет проекта: производительность → надёжность → удобство → расширяемость

## 1. Цель проекта

Создать новую складскую систему для реальной ежедневной работы кладовщика на базе LibreOffice, которая:

- сохраняет привычные листы `Заказы` и `Выдачи`;
- значительно автоматизирует приход, выдачу, возвраты, контроль заказов и документов;
- сохраняет все существующие физические EI-коды;
- рассчитана минимум на 100 000+ движений;
- не выполняет полные пересчёты книги после обычной операции;
- работает полностью офлайн;
- работает на рабочем Ubuntu-компьютере без установки дополнительного ПО;
- позволяет добавлять крупные функции отдельными модулями и Calc-инструментами, не утяжеляя основную WMS;
- допускает дальнейшее развитие ChatGPT + Claude через GitHub без зависимости от истории текущего чата.

Исходное требование прямо запрещает архитектуру, где изменение одной ячейки запускает повторное сканирование всей книги, и требует точечных обновлений, индексов и пакетной обработки.

## 2. Рабочая среда

Основной пользователь: один кладовщик.

Основная рабочая машина:

- Linux Ubuntu;
- LibreOffice;
- интернет для работы WMS не требуется;
- дополнительное ПО устанавливать нельзя;
- возможность запуска portable-программ не считается гарантированной и в первой архитектуре не используется.

Разработка и часть тестирования могут выполняться на Windows, но рабочая версия обязана корректно работать на Linux.

Система должна быть максимально независима от версии ОС и не использовать Windows-only технологии.

## 4. Главный архитектурный принцип

Основная WMS не должна превращаться в огромную книгу с постоянно работающими формулами, обработчиками и отчётами.

Архитектура:

маленькое быстрое складское ядро + подключаемые модули + отдельные Calc-инструменты для тяжёлых задач.

Обычная операция должна затрагивать только:

- текущую строку;
- конкретный EI;
- конкретный заказ;
- соответствующий остаток;
- несколько небольших индексов.

Она не должна пересчитывать весь склад.

Тяжёлые действия выполняются:

- по отдельной кнопке;
- пакетно;
- либо в отдельном ODS-файле.

## 5. Рекомендуемая архитектура первой версии

### Вариант A — Calc + LibreOffice Basic + внутреннее событийное ядро

Это рекомендуемый вариант для первого рабочего релиза.

Пользователь работает непосредственно в Calc.

Внутри книги существуют небольшие служебные структуры:

- реестр всех EI;
- реестр проведённых операций;
- карта текущих остатков;
- индексы;
- счётчики;
- настройки;
- состояние транзакции;
- индекс архивов.

Они не размещаются дополнительными колонками в `Заказы` или `Выдачи`.

#### Преимущества

- ничего не требуется устанавливать;
- минимальный риск несовместимости на рабочем Ubuntu;
- привычный интерфейс;
- быстрый старт разработки;
- можно постепенно заменять отдельные части позже;
- проще аварийное восстановление;
- проще перенос проекта между компьютерами.

#### Основной риск

Calc/Basic имеет предел производительности.

Поэтому архитектура A принимается только если нагрузочные тесты подтверждают целевые показатели.

## 6. Альтернативная архитектура B — Calc + LibreOffice Base/Firebird

Calc остаётся интерфейсом, а движения и индексы находятся в базе.

Потенциально это лучше при очень больших объёмах.

Но предыдущие попытки показали риски:

- проблемы embedded Firebird;
- проблемы совместимости версий;
- проблемы сохранения/повторного открытия базы;
- зависания;
- необходимость очень внимательно тестировать транзакции.

Поэтому Base не является основой первого релиза.

До возможного перехода требуется отдельный технический прототип:

`создание → запись → commit → закрытие LibreOffice → повторное открытие → чтение → rollback → аварийное завершение → нагрузочный тест`.

Если он не проходит абсолютно стабильно на рабочем Ubuntu — Base не используется.

## 7. Альтернативная архитектура C — отдельное приложение/движок

С технической точки зрения это наиболее масштабируемое решение.

Но для текущего проекта оно не подходит как первая версия, поскольку на рабочий компьютер нельзя устанавливать дополнительное ПО.

Архитектуру следует проектировать так, чтобы однажды можно было вынести движок наружу, но WMS v1 не должна от этого зависеть.

## 8. Архитектурное решение v0.1

Рекомендация:

начинаем с варианта A.

При этом:

- данные организуем так, чтобы их потом можно было перенести в БД;
- интерфейс отделяем от складской логики;
- тяжёлую аналитику выносим наружу;
- не создаём тысячи формул;
- не используем глобальные обработчики на каждое изменение ячейки;
- индекс является ускорителем, но не единственным источником истины;
- индекс можно полностью перестроить.

Если Calc-only не пройдёт нагрузочное испытание, решение пересматривается до миграции рабочих данных.

## 9. EI — главный идентификатор склада

Формат новой нумерации:

`ЕИ-00000001` и далее.

Уже существующие EI сохраняются абсолютно без изменений.

Существующие физические наклейки являются частью фактической системы склада. Исходные требования запрещают их перенумеровывать, повторно использовать или молча исправлять.

Правила:

- EI никогда не используется повторно;
- EI нельзя автоматически менять;
- новый номер выдаётся только после проверки максимального существующего;
- один обычный фактический приход создаёт свой EI;
- одинаковость названия обычных товаров специально не ищется;
- система не пытается объединять обычные партии;
- `Наличие` относится именно к конкретному EI;
- выдача осуществляется строго по введённому EI;
- если этого остатка недостаточно, выдача блокируется;
- система не ищет автоматически другой EI такого же товара.

Это значительно уменьшает сложность и нагрузку.

## 10. Специальное правило `Детали`

`Детали` — единственное исключение из правила новых EI.

Для `Площадка / Поставщик = Детали`:

- артикул является ключом;
- существующий артикул → используется существующий EI;
- после ввода артикула название подставляется автоматически;
- новый артикул → вводится новое название → создаётся новый EI;
- одинаковые артикулы деталей запрещены;
- количество увеличивает остаток существующего EI;
- один EI детали может использоваться длительное время независимо от количества производственных поступлений.

Автоматический поиск похожих товаров по названию для обычных приходов не выполняется.

## 11. Виды поступления через `Заказы`

Колонка `Площадка / Поставщик` определяет сценарий.

### Обычный поставщик

В колонке указывается фактический поставщик или площадка.

Обычный процесс:

`Заказ → ожидание → фактическое поступление → УПД → EI → остаток`.

### `Офис`

Специальный приход из офиса.

Минимальные ручные данные:

- название;
- количество;
- единица измерения;
- дата;
- место хранения.

Остальное, включая внутренний код и технические значения, заполняется автоматически.

### `Производство`

Аналогичная упрощённая приёмка.

В `Продавец` указывается человек, передавший товар.

### `Детали`

Производственные детали с обязательным артикулом и специальным правилом EI.

### `Старый склад`

Используется при постепенной постановке старого немаркированного склада на учёт.

Позиция не считается существующей в новой WMS, пока пользователь физически её не разобрал, не пересчитал и не внёс.

Одна обнаруженная физическая позиция → один новый EI.

Нельзя заранее импортировать огромный неподтверждённый список старого склада.

## 12. Автоматические номера специальных приходов

Разные сценарии получают разные внутренние номера:

- `OFF-...` — офис;
- `PROD-...` — производство;
- `DET-...` — детали;
- `OLD-...` — старый склад.

Точный числовой формат и длина настраиваются.

## 13. Заказ и частичные поступления

Один заказ может иметь:

- один счёт;
- несколько УПД;
- разные даты поступления;
- частичные поступления.

Пример:

Заказано: `100`

УПД №1 → 20

УПД №2 → 30

УПД №3 → 50

Каждый новый УПД является отдельным фактическим поступлением, но относится к тому же номеру заказа и счёту.

Один УПД может содержать много разных товарных позиций.

Каждая позиция обрабатывается отдельно.

Для обычных товаров каждая фактическая позиция поступления получает свой EI.

## 14. Три количества заказа

Сохраняется различие:

Заказанное количество — сколько хотели получить.

Количество по документу — сколько указано в УПД/накладной.

Фактическое количество — сколько реально принято физически.

Контроль:

`Документ = Факт` → всё корректно.

`Документ > Факт` → недостача.

`Документ < Факт` → излишек относительно документа.

Заказанное количество не переписывается после частичного поступления.

## 15. Статусы заказа

Минимальный набор:

- `Ожидается`;
- `Просрочено`;
- `Частично получено`;
- `Получено`;
- `Получено без документов`;
- `Отменён`;
- `Частично получено / остаток отменён`.

Логика:

есть счёт, но нет фактического прихода → ожидается;

есть фактический приход, но нет закрывающего документа → товар физически принят, документы ожидаются;

факт и документы присутствуют → получено;

оставшаяся неполученная часть может быть отменена.

Полученное количество при отмене остатка заказа не изменяется.

## 16. Отмена заказа

Поддерживаются:

### Полная отмена

Если ничего ещё не поступило.

### Отмена остатка

Например:

заказано 100;

получено 40;

оставшиеся 60 отменены.

Система сохраняет:

- заказанное = 100;
- получено = 40;
- ожидание оставшихся 60 прекращается.

История не уничтожается.

## 17. Выдачи

Основной быстрый сценарий должен быть максимально коротким:

`EI → количество → кому → провести`.

После ввода EI автоматически подгружаются известные данные:

- наименование;
- артикул;
- единица;
- категория;
- место хранения;
- текущий остаток.

Место хранения берётся автоматически из карточки EI.

Один EI в каждый момент имеет одно текущее место хранения.

Если EI не существует среди проведённых поступлений:

проведение полностью блокируется.

Если остаток EI = 0:

проведение полностью блокируется.

Если пытаются выдать больше остатка:

проведение полностью блокируется.

Никакого автоматического списания с другого EI.

## 18. Получатели и сокращения

Получателем может быть:

- человек;
- `Офис`;
- `Производство`;
- другое текстовое значение.

Основной ввод остаётся свободным текстом.

Добавляется лёгкий справочник сокращений.

Пример:

`егр` → `Ермолин Егор Павлович`

У одного человека одно сокращение.

Сокращение уникально.

Ввод сокращения подставляет полное имя.

Ввод полного имени позволяет системе определить сокращение.

## 19. История выдач по получателю

Отдельный пользовательский лист.

Это не утверждение, что товар физически до сих пор находится у человека.

Он показывает историю:

- кому выдавалось;
- EI;
- наименование;
- количество;
- дата;
- возвраты.

Можно выбрать:

`Петя`, `Офис`, `Производство` и т. д.

Склад после выдачи не отслеживает, использовал человек расходник или нет.

## 20. Возврат

Возврат оформляется на отдельном листе `Возврат`.

Минимальный ввод:

- EI;
- количество;
- кто вернул;
- дата;
- место возврата.

Название и остальные известные данные подгружаются автоматически.

Поддерживается:

- частичный возврат;
- несколько возвратов одной выдачи;
- возврат одним получателем одного EI после нескольких выдач.

Возврат не обязан связываться с конкретной исходной строкой выдачи.

Он уменьшает суммарно выданное этому получателю количество соответствующего EI.

Если возврат превышает ранее выданное количество этому получателю:

операция блокируется.

Вернуть товар может и другой человек — при условии корректного EI и количества.

Место возврата выбирается вручную.

## 21. Проценты

`Количество в %` рассчитывается относительно исходного количества конкретного EI.

Пример:

пришло 20 кг;

выдали 25% → 5 кг.

Поддерживаются дробные количества.

## 22. Единицы измерения

Один товар может использовать конверсию единиц.

Коэффициент задаётся для конкретного товара.

Пример:

`1 упаковка = 1000 шт.`

Хранилище должно иметь однозначную базовую единицу, чтобы остаток не расходился.

## 23. `Иной приход`

Отдельная зона для физически присутствующего, но пока не идентифицированного товара.

Он:

- считается складским остатком;
- получает EI сразу;
- находится в состоянии разбора;
- после идентификации переводится в нормальный `Заказы`;
- исходная рабочая запись может быть убрана после перевода;
- история технического переноса сохраняется внутри системы.

При переводе EI сохраняется.

Если неизвестная позиция позднее разделяется на несколько товаров:

- одна часть сохраняет первоначальный EI;
- остальные получают новые EI.

Двойного учёта быть не должно.

## 24. Наличие

Отдельный лист `Наличие` сохраняется.

Для каждого EI:

- код;
- название;
- артикул;
- единица;
- текущее количество;
- место;
- категория;
- состояние.

Допускаются EI с нулевым остатком.

Но этот лист не должен быть источником истины сам по себе.

Его содержимое должно обновляться точечно.

## 25. Исправление проведённых операций

Для пользователя должны существовать удобные действия:

- `Исправить`;
- `Удалить`.

Но физически уничтожать уже повлиявшую на остаток операцию опасно.

Внутри система выполняет безопасную коррекцию:

1. отменяет влияние старой операции;
2. создаёт исправленную операцию;
3. обновляет остаток;
4. старая пользовательская строка может быть скрыта/заменена.

Таким образом для пользователя это выглядит как обычное исправление или удаление, но целостность системы сохраняется.

## 26. Минимальный технический аудит

Пользовательский большой `Журнал всех операций` не требуется.

Но для безопасности необходим небольшой служебный реестр:

- Operation ID;
- тип операции;
- состояние `STARTED / COMMITTED / CANCELLED`;
- EI;
- ссылка на источник;
- дата;
- контрольная информация.

Он нужен только для:

- защиты от двойного проведения;
- восстановления после аварии;
- безопасного исправления;
- диагностики.

## 27. Защита от двойного клика

Каждая проводимая операция получает уникальный Operation ID.

Повторный клик `Провести` не должен создавать второй приход или расход.

## 28. Восстановление после падения LibreOffice

Если LibreOffice аварийно закрывается во время операции:

после следующего запуска WMS должна определить:

- операция не начиналась;
- операция началась, но не завершилась;
- операция была полностью проведена.

Повторное нажатие не должно создавать дубль.

## 29. Индексы

Для быстрого поиска поддерживаются небольшие индексы:

- EI;
- артикулы `Деталей`;
- документы;
- номер заказа;
- получатели;
- сокращения;
- открытые заказы;
- архивный EI.

Индекс:

- ускоряет работу;
- не является необратимым источником данных;
- должен восстанавливаться кнопкой `Перестроить индексы`.

Полное построение индекса запускается отдельно, а не после каждой строки.

## 30. Антидубль

Контроль возможных дублей выполняется по лёгкому ключу, например комбинации:

`поставщик + документ + артикул + количество + дата`.

Проверяется индекс, а не весь лист.

Подозрение отображается в существующей колонке `Возможный дубль`.

Окончательное решение остаётся за пользователем.

## 31. Настройки

Нужен полноценный `Настройки WMS`.

Через настройки управляются:

- включение/отключение дополнительных модулей;
- обязательные поля;
- форматы автоматических номеров;
- категории;
- места хранения;
- справочник получателей;
- сокращения;
- коэффициенты единиц;
- пороги предупреждений;
- архивирование;
- отчёты;
- печать;
- диагностика;
- режим разработчика;
- Safe Mode;
- версии модулей.

Настройки читаются в память при запуске.

Макрос не должен постоянно сканировать лист настроек.

## 32. Главная

Лист `Главная` допускается, если он не создаёт постоянной нагрузки.

Он работает через небольшой кэш.

На нём можно отображать:

- ожидаемые заказы;
- просроченные;
- поступления без документов;
- ошибки;
- возможные дубли;
- `Иной приход`;
- последние операции;
- краткое состояние WMS.

Не должно быть сотен постоянно пересчитываемых формул.

## 33. Комплекты

Отдельные листы:

`Комплекты`

и

`Состав комплектов`.

Комплект определяет набор товаров/позиций.

Пример:

`Комплект монтажника №1`

содержит:

- товар A × 2;
- товар B × 1;
- товар C × 10.

При работе с комплектом система один раз проверяет состав и наличие, затем создаёт обычные складские выдачи.

Никаких постоянных пересчётов комплектов в фоне.

## 34. Акты и Writer

Нужна автоматизация всех основных актов:

- обычные приходы;
- производство;
- офис;
- выдачи;
- возвраты;
- другие согласованные операции.

Разным операциям соответствуют разные шаблоны.

Отдельный рабочий лист позволяет вставить/выбрать данные и нажать нужную кнопку.

Результат:

- ODT в LibreOffice Writer;
- правильный шаблон;
- автоматическая нумерация;
- журнал уже использованных номеров;
- защита от случайного повторения номера.

PDF не является обязательным.

## 35. Учёт автомобилей

Функция сохраняется как требование проекта.

Но она не должна задерживать основной запуск WMS.

Разрабатывается отдельным модулем после ядра с использованием фактической логики текущей системы.

## 36. Принтер этикеток

Печать не является зависимостью WMS.

Если существующий Xprinter удаётся использовать средствами уже настроенной ОС/LibreOffice без установки дополнительного программного обеспечения:

добавляется кнопка `Печать этикетки`.

Этикетка:

- название;
- EI.

Если системная печать недоступна — модуль отключён, работа WMS никак не меняется.

## 37. Реестр EI

В основной системе навсегда существует компактный реестр всех EI, включая нулевые и архивные.

Минимально:

`EI | Название | Артикул | Единица | Остаток | Статус | Источник истории`

Даже если EI полностью выдан много лет назад, номер не исчезает.

## 38. Архивирование

Архивируется история движений, а не сам EI.

Кандидат:

- остаток = 0;
- нет незавершённых операций;
- нет ожидающих действий;
- данные достаточно старые.

Положительный остаток не архивируется.

Для `Деталей` карточка артикула/EI остаётся активной всегда.

Архивирование запускается вручную:

`Проверить кандидатов → показать результат → Архивировать`.

## 39. Возврат архивного товара

Если EI имел остаток 0 и его старая история уже находится в архиве, а потом вернули 2 шт.:

- EI находится через постоянный реестр;
- остаток становится 2;
- EI вновь активируется;
- товар можно снова выдать.

Новый EI не создаётся.

## 40. WMS_ARCHIVE_MANAGER.ods

Отдельный инструмент:

- поиск кандидатов;
- проверка нулевого остатка;
- создание архивных файлов;
- индекс архивов;
- проверка целостности;
- просмотр архивов;
- восстановление данных при необходимости.

Редкая тяжёлая работа не нагружает ежедневную WMS.

## 41. WMS_РАЗБОР_АРХИВА.ods

Полностью отдельная система.

Она никогда ничего не импортирует автоматически в рабочую WMS.

Предназначение:

- вставить около 5000 правильных старых поступлений;
- вручную переписать около 4000 бумажных выдач;
- помочь определить, какой старый текст соответствует какому товару.

Старые записи могут иметь формы:

`м8х10`

`М8X10`

`m8x10`

`болт 8х10`

и т. п.

Нужна нормализация:

- регистр;
- латинская/кириллическая X/Х;
- пробелы;
- дефисы;
- размеры;
- сокращения;
- перестановки слов;
- единицы измерения.

Результат:

`ТОЧНО`

`ВЕРОЯТНО`

`ВОЗМОЖНО`

`НЕ НАЙДЕНО`

и несколько кандидатов.

Решение всегда принимает пользователь.

После разбора пользователь сам переносит нужные данные в рабочую WMS.

## 42. WMS_REPORTS.ods

Отдельный инструмент только для ежедневного отчёта руководителю.

Старая система уже предусматривала отдельные `Отчет_ввод`, `Отчет руководителю` и `История отчетов`.

Старый формат включал:

- дату;
- завершённое сегодня;
- задачи на следующий день;
- задачи в процессе;
- готовый текст для копирования.

Новая версия расширяет это.

Основная WMS по кнопке создаёт маленький снимок выбранного дня.

`WMS_REPORTS.ods` автоматически получает:

- поступления;
- выдачи;
- возвраты;
- новые EI;
- частичные приходы;
- заказы без документов;
- отмены;
- просрочки;
- операции производства;
- офис;
- детали;
- старый склад;
- акты;
- выявленные проблемы.

Пользователь вручную добавляет деятельность, которую WMS не знает.

Например:

- разгрузки;
- взаимодействие с бухгалтерией;
- закупки;
- АХО;
- производство;
- водители;
- другие задачи.

Формируется один ежедневный отчёт.

Система автоматически исключает пустые блоки.

Перед сохранением весь итоговый отчёт можно вручную изменить, включая автоматически подставленные цифры.

Для выбранной даты существующий отчёт может быть перезаписан.

Есть кнопка `Скопировать отчёт`.

Дополнительно можно автоматически показать сравнение с предыдущим рабочим днём.

## 43. WMS_ANALYTICS.ods

Полностью отдельная аналитическая система.

Основная WMS не должна постоянно выполнять эту аналитику.

Данные поступают через единый read-only снимок.

Поддерживается:

- вся текущая история;
- холодные архивы;
- произвольные периоды;
- сегодня;
- 7 дней;
- 30 дней;
- 90 дней;
- год;
- свой период.

### Аналитика расхода

- поступления;
- выдачи;
- возвраты;
- чистый расход;
- оборот;
- наиболее расходуемые товары;
- наиболее активные категории;
- получатели;
- производство;
- офис;
- детали.

Возвраты уменьшают фактический расход.

### Прогноз

Основная единица прогноза:

товар/артикул, а не отдельный обычный EI.

EI используются для фактического остатка.

Для деталей прогноз строится по артикулу.

Система может определять:

- средний расход;
- скорость расходования;
- сколько дней хватит;
- приблизительную дату исчерпания;
- автоматически рассчитанный минимальный остаток;
- рекомендуемое количество следующего заказа;
- необходимость закупки;
- риск дефицита до следующего ожидаемого поступления.

Учитываются:

- физический остаток;
- расход;
- возвраты;
- средний срок поставки;
- уже заказанное, но ещё не пришедшее количество;
- частично полученные заказы;
- отменённые остатки заказа исключаются.

Если данных мало или поведение нестабильно:

`Недостаточно данных / прогноз ненадёжен`.

Система не должна выдумывать точность.

### Автоматическая рекомендация закупки

Рекомендация появляется только если история действительно показывает регулярное потребление/заказы.

Разовая позиция не должна автоматически попадать в `Заказать`.

### Поставщики

Без отдельного анализа изменения закупочных цен.

Но нужны объективные показатели:

- количество заказов;
- средний срок;
- задержки;
- недопоставки;
- расхождение документ/факт;
- отсутствие документов.

### Залежавшиеся остатки

Отдельные категории:

- 30 дней;
- 90 дней;
- 180 дней.

### Нагрузка склада

- число поступлений;
- выдачи;
- количество строк;
- пиковые дни;
- средняя нагрузка;
- сравнение дней;
- статистический прогноз нагрузки.

### Работа кладовщика

Можно анализировать:

- обработанные операции;
- новые EI;
- старый склад;
- `Иной приход`;
- акты;
- другие измеримые действия.

### Dashboard

Допускаются диаграммы и расширенная аналитика.

Но ничего тяжёлого автоматически при открытии.

Обновление только кнопкой:

`Обновить аналитику`.

## 44. Единый формат обмена между инструментами

Основная WMS создаёт один стандартный read-only снимок.

Его используют:

- REPORTS;
- ANALYTICS;
- другие внешние Calc-инструменты.

Это уменьшает количество разного экспортного кода.

Внешние инструменты не имеют права записывать обратно в рабочую WMS.

## 45. Другие независимые инструменты

Архитектура предусматривает последующее создание:

- `WMS_RECONCILE.ods` — сверка с бухгалтерией/закупками;
- `WMS_TEST_LAB.ods` — функциональный тестовый стенд;
- `WMS_BENCHMARK.ods` — нагрузочные тесты;
- инструмент миграционного аудита;
- инструмент контроля документов;
- при необходимости отдельный центр актов.

Их отсутствие не блокирует первый релиз.

## 46. Производительность

Текущий объём:

около 2000 поступлений в месяц;

3000+ выдач в месяц.

Прогноз:

100 000+ движений обязателен.

Нагрузочные испытания должны включить:

- 10 000;
- 50 000;
- 100 000;
- 250 000;
- желательно 500 000 движений.

Целевой отклик обычных ежедневных операций:

примерно ≤ 0,5 секунды на рабочем компьютере.

Это цель, а не обещание.

Если она физически недостижима на конкретном оборудовании, результат теста должен быть показан честно до миграции.

## 47. Запрещённые производительные решения

Нельзя:

- после выдачи полностью пересчитывать `Заказы`;
- после прихода сканировать весь `Выдачи`;
- при вводе обычного товара искать все похожие названия;
- постоянно перестраивать dashboard;
- хранить сотни тяжёлых volatile-формул;
- запускать несколько обработчиков одного события;
- выполнять глобальную диагностику после каждого изменения;
- открывать и анализировать холодные архивы во время обычной выдачи.

## 48. Пакетные операции

Для массовых данных:

`Вставить → Проверить пакет → показать ошибки → Провести`.

Проверки выполняются один раз на пакет.

До проведения отображается результат:

- сколько корректно;
- сколько ошибок;
- сколько дублей;
- сколько создаст EI.

- дубли EI;
- конфликт артикулов деталей;
- отрицательные остатки;
- битые индексы;
- неизвестные EI;
- повреждённые связи;
- конфликт сокращений;
- незавершённые операции;
- счётчики;
- структуру обязательных листов;
- установленные версии модулей.

Диагностика не работает постоянно.

## 50. Safe Mode

Если дополнительный модуль ломается:

можно отключить:

- dashboard;
- аналитику;
- печать;
- дополнительные подсказки;
- отчётные функции.

Основной контур:

`Приход → EI → Остаток → Выдача → Возврат`

продолжает работать.

## 51. Режим разработчика

Включается только при тестировании.

Содержит:

- расширенный лог;
- измерение времени;
- диагностические данные;
- служебные проверки.

В рабочем режиме отключён.

## 52. Миграция существующей WMS

Старая WMS остаётся рабочей до момента финального переключения.

Нельзя проводить миграцию сразу на production-книге.

Обязательный порядок:

1. Копия текущей рабочей книги.
2. Инвентаризация всех существующих EI.

4. Определение максимального EI.

8. Импорт существующих фактических приходов.
9. Сохранение исходных количеств поступлений.
10. Сухой прогон.
11. Сверка количества строк.
12. Сверка EI.
13. Сверка остатков.
14. Выборочная физическая проверка наклеек.
15. Тест выдачи по старым EI.
16. Проверка отката.
17. Только после этого финальное переключение.

## 53. Старые бумажные выдачи

Текущая проблема:

часть выдач существующих EI записывалась на бумаге.

Известны:

- EI;
- количество;
- получатель;
- дата.

Остальные данные должны подгружаться из соответствующего прихода.

Они должны в итоге стать историческими операциями `Выдачи`, чтобы фактический остаток рассчитывался правильно.

Разбор текста помогает выполнить отдельный `WMS_РАЗБОР_АРХИВА.ods`.

Автоматической записи в рабочую WMS он не делает.

## 54. Источник истины

Для физического состояния склада источник истины — проведённые складские операции.

`Наличие` является быстрым представлением текущего результата.

`Заказы` является рабочим вводом заказа/поступления.

`Выдачи` является рабочим вводом расхода.

`Возврат` создаёт обратное складское движение.

Индексы являются производительным кэшем и могут быть восстановлены.

## 59. Протокол ChatGPT ↔ Claude

Никакого прямого автоматического общения между моделями не предполагается.

Общий канал — проектные файлы в GitHub.

Процесс:

1. Пользователь + ChatGPT

   Принимают бизнес-решения.

2. ChatGPT

   Обновляет MASTER SPEC и DECISIONS.

3. Claude

   Перед каждым заданием обязан прочитать:

   - MASTER SPEC;
   - DECISIONS;
   - STATE;
   - конкретный TASK.

4. Claude

   Не должен придумывать новые бизнес-правила.

   Если видит проблему — пишет её в отчёт.

5. После работы Claude

   обновляет REPORT и предлагает изменения STATE.

6. ChatGPT

   анализирует результат, тесты и замечания.

7. Пользователь

   утверждает следующий шаг.

## 60. Первое задание Claude — НЕ писать код

Первым заданием должно стать архитектурное ревью этой спецификации.

Claude должен:

- проверить противоречия;
- найти слабые места;
- найти потенциальные тормоза;
- найти места потери данных;
- оценить Calc-only для 100k+;
- предложить упрощения;
- оценить стратегию индексов;
- оценить безопасное проведение без служебных колонок в `Заказы/Выдачи`;
- оценить crash recovery;
- оценить миграцию EI;
- предложить минимальную архитектуру, которую можно быстрее всего вывести в production;
- перечислить, что из функций следует отложить;
- предложить тесты.

Он не создаёт никакого кода.

После его отчёта решения снова утверждаются пользователем.

## 61. Высокорисковые технические прототипы

До массовой разработки необходимо отдельно доказать четыре вещи:

### Прототип 1 — идентичность строки без новых колонок

Как надёжно связывать пользовательскую строку `Заказы/Выдачи` со служебной операцией без добавления служебного ID в неизменяемые листы.

### Прототип 2 — скорость

Проведение и поиск EI при 100k+ движений.

### Прототип 3 — аварийное восстановление

Прервать проведение посередине и доказать отсутствие двойного движения.

### Прототип 4 — сохранение и повторное открытие

Закрыть LibreOffice, перезагрузить документ и подтвердить сохранность состояния и индексов.

Если эти четыре проверки не пройдены, полноценная разработка дальше не идёт.

## 62. Критерии первого рабочего релиза

Release 1 нельзя считать готовым, пока не выполнены одновременно:

- `Заказы` A не изменены;
- `Выдачи` A не изменены;
- все старые EI сохранены;
- новый EI не конфликтует со старым;
- выдача неизвестного EI невозможна;
- отрицательный остаток невозможен;
- повторный `Провести` не создаёт дубль;
- частичный приход работает;
- несколько УПД работают;
- детали повторно используют EI по артикулу;
- возвраты работают частями;
- исправление не ломает остаток;
- аварийное закрытие не создаёт двойной операции;
- данные после закрытия/открытия сохраняются;
- миграционный отчёт сходится;
- нагрузочный тест пройден;
- обычная работа на рабочем Ubuntu субъективно и измеримо быстрая.

## 63. Что намеренно НЕ делаем в ядре

Чтобы не затягивать запуск:

- fuzzy-поиск обычных товаров;
- постоянный глобальный поиск;
- автоматическую инвентаризацию;
- перемещения между несколькими складами;
- отдельный процесс списания;
- постоянную тяжёлую аналитику;
- недельные/месячные отчёты;
- обязательный сканер;
- обязательную печать;
- Base/Firebird без доказанного преимущества;
- внешний сервис;
- автоматическую интеграцию архивного распознавателя с production.

## 66. Основной принцип проекта

Новая WMS не должна пытаться быть огромной ERP.

Она должна быть:

быстрой в ежедневной работе;

предсказуемой;

восстанавливаемой;

не уничтожающей историю;

не зависящей от интернета;

не зависящей от дополнительного ПО;

удобной для одного кладовщика;

и расширяемой отдельными инструментами без переделки ядра.
