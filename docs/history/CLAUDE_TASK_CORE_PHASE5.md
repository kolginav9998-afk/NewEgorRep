CORE PHASE 5 PRIME — ВСЕ СПЕЦИАЛЬНЫЕ ПРИХОДЫ
ЦЕЛЬ ЭТАПА
Сделать одним большим этапом весь оставшийся контур поступлений товара в основную WMS.
После Phase 5 WMS должна поддерживать практически все реальные способы появления товара на складе:

1. обычный заказ / обычный поставщик — уже реализовано;
2. Офис;
3. Производство;
4. Детали;
5. Старый склад;
6. Иной приход / неопознанный или нестандартный приход.

Нужно получить единую рабочую систему:
`любой приход → правильный EI → Наличие → Выдача → Возврат → актуальный остаток`
без отдельных несовместимых механизмов.

2. убедиться, что working tree clean;
3. записать hash принятого Phase 4 в отчёт и `WMS_STATE.md`.

`claude/festive-lamport-l4f8f1`
Не менять `main`.
GIT
До отдельной приёмки Phase 5:
НЕ выполнять:

* commit;

Сначала:
архитектура → реализация → тесты → oracle → benchmark → отчёт → приёмка пользователя.
ГЛАВНЫЙ ПРИНЦИП
Не создавать пять независимых систем прихода.
Нужен один общий движок поступления, поверх которого разные источники имеют собственные правила.
Общий уровень должен отвечать за:

* EI;
* атомарность;
* журнал;
* `Наличие`;
* место хранения;
* количество;
* единицу;
* категорию;
* защиту;
* recovery;
* storno;
* исправление;
* связь с выдачами/возвратами;
* антидубли;
* отображение остатка.

Специфика источника должна отвечать только за:

* обязательные поля;
* тип идентификатора;
* создание нового EI или пополнение существующего;
* правила артикула;
* документы;
* UI.

Не копировать большой кусок `WmsReceipt` пять раз.
ИСТОЧНИКИ
Поддержать следующие типы:
`Поставщик`
`Офис`
`Производство`
`Детали`
`Старый склад`
`Иной приход`
Обычный `Поставщик` уже работает через Phase 3 и должен остаться полностью совместимым.
АВТО-ID ИСТОЧНИКОВ
Для специальных приходов используются собственные идентификаторы событий:

* `OFF-00000001`
* `PROD-00000001`
* `DET-00000001`
* `OLD-00000001`
* для Иного прихода определить безопасный формат, предпочтительно `OTH-00000001`, если MASTER SPEC не фиксирует другой.

Это НЕ EI.
Один такой ID относится к одному событию приёмки и может включать несколько товарных строк.
Пример:
одна передача из производства из 7 позиций:
все 7 строк имеют:
`PROD-00000125`
но каждая физическая партия может иметь собственный EI по правилам источника.
Счётчики:

* NEXT_OFF
* NEXT_PROD
* NEXT_DET
* NEXT_OLD
* NEXT_OTH

или эквивалентная безопасная схема.
Номера:

* монотонны;
* не переиспользуются;
* учитываются recovery/ABANDON;
* не конфликтуют между источниками.

Если схема `_SYS` требует расширения — сделать миграционно безопасно и документировать.
UI
Пользователь не должен разбираться во внутренних типах операций.
Нужен понятный рабочий интерфейс.
Допустимы два подхода:
Вариант A — единый лист специального прихода
`Иной приход`
с выбором типа:

* Офис;
* Производство;
* Детали;
* Старый склад;
* Иной.

Вариант B — существующие отдельные пользовательские листы
если они уже предусмотрены архитектурой и это удобнее пользователю.
Сначала проверить MASTER SPEC и текущую книгу.
Не создавать лишние листы без необходимости.
Общее правило:
обычные заказы остаются на `Заказы`.
Специальные приходы не должны ломать обычные заказы.
ОФИС
Сценарий:
товар/имущество поступило со стороны офиса без обычного заказа поставщику.
Минимальные обязательные поля:

* наименование;
* количество;
* единица;
* дата поступления;
* место хранения.

Дополнительно:

* артикул — если есть;
* категория;
* кто передал;
* комментарий;
* документ — если есть.

Документ не обязателен.
Каждая новая физическая партия обычного офисного прихода получает новый EI.
Одинаковое название и артикул не объединяют партии автоматически.
ПРОИЗВОДСТВО
Сценарий:
из цеха/производства поступила изготовленная продукция или материальная позиция.
Минимально:

* наименование;
* количество;
* единица;
* дата;
* место.

Артикул:

* может отсутствовать.

Документ:

* может отсутствовать.

Поле `Продавец` / эквивалент при производстве может использоваться как:
`Кто передал`
если текущая структура это позволяет.
Новая отдельная партия производства → новый EI.
ПРОИЗВОДСТВО И ДЕТАЛИ
Пользователь ранее зафиксировал:
Приход производства и приход деталей должны использовать единый механизм.
Различие:

* у производства артикул может отсутствовать;
* у деталей артикул — ключевой.

Не создавать два полностью разных ядра.
ДЕТАЛИ — КРИТИЧЕСКИЙ СЦЕНАРИЙ
Для `Детали` действует особое правило:
один уникальный артикул → один основной EI.
Если артикул уже существует в активном реестре деталей:
новый приход НЕ создаёт новый EI.
Он:

* использует существующий EI;
* увеличивает его остаток;
* сохраняет название из существующей карточки;
* добавляет отдельное событие прихода в журнал/историю;
* обновляет `Наличие`;
* обновляет отражение остатка.

Пример:
артикул:
`ABC-100`
первый приход:
100 шт → `ЕИ-00000421`
через месяц:
ещё 50 шт `ABC-100`
результат:
тот же `ЕИ-00000421`
остаток:

150. 

ДЕТАЛИ — НАЗВАНИЕ
Если артикул найден:
каноническое название берётся из существующего EI.
Если пользователь ввёл другое название:
не создавать новый EI автоматически.
Показать предупреждение:
`Артикул уже существует: ЕИ-..., название «...». Будет использовано существующее наименование.`
Если различие выглядит серьёзным — дать понятный контроль.
ДЕТАЛИ — КОНФЛИКТЫ
Нужно обрабатывать:

1. один артикул → один EI — нормальный случай;
2. один артикул найден у двух EI — системный конфликт;
3. пустой артикул для `Детали` — отказ;
4. артикул отличается только регистром/пробелами/типовыми символами — нормализовать;
5. старые исторические конфликты не исправлять автоматически.

При конфликте:
FAIL-CLOSED.
Показать:
`Для артикула ... найдено несколько EI. Требуется разбор.`
Не выбирать один случайно.
ИНДЕКС ДЕТАЛЕЙ
Нельзя каждый приход сканировать по всему `Наличие`.
Нужен быстрый индекс:
`normalized article → EI`
Подход должен соответствовать архитектуре:

* Calc engine;
* плотная служебная таблица;
* ленивый/проверяемый индекс;
* либо другой O(1)-подобный механизм.

После миграции индекс должен перестраиваться/проверяться.
СТАРЫЙ СКЛАД
Это НЕ массовая миграция старого файла.
Это рабочий сценарий:
кладовщик физически находит старый товар, которого ещё нет в новой WMS.
Вводит:

* название;
* артикул если есть;
* фактическое количество;
* единицу;
* место;
* категорию;
* комментарий;
* при необходимости старую маркировку.

После проведения:

* создаётся новый EI;
* товар становится обычным остатком;
* источник = Старый склад;
* операция получает OLD-ID;
* товар дальше работает со стандартной выдачей и возвратом.

Никакого массового предварительного заполнения Старого склада в этом этапе.
ИНОЙ ПРИХОД
Нужен карантинный / универсальный сценарий для вещей, которые нельзя корректно классифицировать в момент поступления.
Примеры:

* непонятно откуда пришло;
* нет документов;
* товар найден;
* временно неизвестна категория;
* обнаружена позиция при разборе склада.

Правило:
Иной приход сразу считается складским остатком.
Он:

* получает EI сразу;
* появляется в `Наличие`;
* может быть выдан по этому EI;
* хранит статус/признак `Требует разбора`.

Поля:

* наименование или временное описание;
* количество;
* единица;
* дата;
* место;
* комментарий;
* фото/ссылка — только если существующая структура это поддерживает без усложнения ядра.

РАЗБОР ИНОГО ПРИХОДА
Нужна возможность позднее определить:

* нормальное название;
* артикул;
* категорию;
* источник.

КРИТИЧЕСКОЕ ПРАВИЛО:
если это всё та же физическая партия, EI сохраняется.
Нельзя при простом уточнении карточки создавать новый EI.
Если одна карантинная позиция позже выяснилась как несколько разных товаров:
разделение требует отдельной атомарной операции.
Если безопасная реализация split слишком сильно раздувает Phase 5:
реализовать распознавание без split сейчас,
а split вынести как отдельное решение на утверждение.
Не делать небезопасную полу-реализацию.
EI
Обычные специальные приходы
Офис → новый EI.
Производство → новый EI.
Старый склад → новый EI.
Иной приход → новый EI.
Детали
Первый уникальный артикул → новый EI.
Повторный приход того же артикула → существующий EI.
EI НИКОГДА НЕ ПЕРЕИСПОЛЬЗУЕТСЯ
Любой сторно, crash, abandon:
не должен привести к повторной выдаче номера, который уже мог быть:

* показан;
* напечатан;
* попал в журнал;
* попал в документ.

Соблюдать правила Phase 1–4.
ПРИХОД В СУЩЕСТВУЮЩИЙ EI
Нужен общий механизм:
`RECEIPT_ADD_EXISTING_EI`
или эквивалент.
Он необходим прежде всего для `Деталей`.
Одна атомарная операция:

* журнал;
* количество прихода;
* новый остаток;
* служебная запись события;
* `Наличие`;
* зеркала остатка;
* источник;
* event ID.

Не превращать существующий EI в новую партию.
СТОРНО СПЕЦИАЛЬНОГО ПРИХОДА
Должны действовать строгие зависимости, принятые после Phase 4.
Нельзя сторнировать приход, если от него существуют действующие зависимые движения.
Для EI обычной отдельной партии:
если есть действующая выдача/возврат:
`RECEIPT_DEL` запрещён.
Сначала:

* storno возвратов;
* storno выдач;
* затем приход.

Для `Деталей`, где один EI пополняется много раз:
нельзя использовать простое правило:
`остаток == количество конкретного прихода`.
Нужно учитывать историю пополнений EI.
Сторно конкретного пополнения возможно только если итоговый остаток не станет меньше уже потреблённого количества.
Пример:
EI детали:
приход 100;
потом приход 50;
выдано 120;
остаток 30.
Сторно второго прихода 50 запрещено:
остаток стал бы −20.
Если выдано 80:
остаток 70;
сторно второго прихода 50 допустимо:
остаток станет 20.
Oracle обязан это проверять.
ИСПРАВЛЕНИЕ СПЕЦИАЛЬНОГО ПРИХОДА
Одна составная операция.
Разрешить исправлять:

* количество;
* дату;
* место;
* документ;
* категорию;
* безопасные атрибуты.

Но:

* EI нельзя произвольно менять;
* источник события нельзя превращать в другой источник без специального сценария;
* для деталей нельзя изменить артикул так, чтобы он стал принадлежать другому существующему EI.

Если требуется сменить идентичность физического товара:
storno + новый приход.
МЕСТО ХРАНЕНИЯ
Один EI = одно текущее место.
Новый приход нового EI:
задаёт место.
Повторный приход `Детали` в существующий EI:
если пользователь указал другое место, система должна:

* предупредить;
* при подтверждении сделать новое место текущим в той же операции;

или, если это архитектурно опасно, запретить и вынести перемещение отдельным решением.
Нельзя тихо менять место.
КАТЕГОРИЯ
Сохраняется в `Наличие`.
У повторного прихода детали:
существующая карточка EI является основой.
Если новая строка предлагает другую категорию:
предупреждение.
Не создавать второй EI только из-за категории.
ЕДИНИЦА
Для нового EI:
единица задаётся приходом.
Для существующего EI детали:
единица должна совпасть.
Пересчёт единиц Phase 5 НЕ реализует.
Если:
существующий EI = `шт`
новый приход того же артикула = `упак`
→ отказ:
`Для EI используется единица шт. Пересчёт единиц не настроен.`
ВНУТРЕННИЕ КОДЫ
Автогенерация EI должна продолжать работать:
`ЕИ-00000001`
и далее.
Ввод вариантов:

* `1`
* `00000001`
* `EI-1`
* `ЕИ-1`

должен нормализоваться в канонический EI там, где пользователь вводит код.
Не менять уже существующие EI.
ВЫДАЧИ
После любого специального прихода EI должен работать в существующем Phase 2 без отдельного кода:
EI → название → остаток → выдача.
Особенно проверить:

* EI Офис;
* EI Производство;
* EI Детали;
* EI Старый склад;
* EI Иной приход.

ВОЗВРАТ
Все такие EI должны работать в Phase 4:
выдача → возврат → тот же EI.
Не создавать отдельную систему возврата для источников.
НАЛИЧИЕ
`Наличие` остаётся единым постоянным реестром.
Одна строка = один EI.
Источник может различаться.
Минимально должен быть понятен источник происхождения EI:

* Поставщик;
* Офис;
* Производство;
* Детали;
* Старый склад;
* Иной приход.

Не создавать отдельные остатки для каждого источника.
При этом в будущем аналитика должна иметь возможность фильтровать остаток по источнику.
ДЕТАЛИ В НАЛИЧИИ
У детали:

* один EI;
* текущий общий остаток всех приходов;
* уникальный артикул;
* каноническое название;
* единица;
* место;
* категория.

История отдельных пополнений хранится в журнале / служебных событиях, а не отдельными EI.
ЗАКАЗЫ.X
Для обычного прихода Phase 3 X остаётся текущим остатком EI.
Для специальных приходов, которые не находятся в `Заказы`, не пытаться создавать фиктивные строки заказа.
