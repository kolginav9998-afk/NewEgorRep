## ОСНОВНОЙ ПРИНЦИП

Создание нового ЕИ и создание его записи в `Наличие` являются частью одной атомарной складской операции прихода.

Недопустимы промежуточные состояния:

* ЕИ уже выдан, а записи в `Наличие` ещё нет;
* строка прихода проведена, а остаток не создан;
* остаток создан, а приход не зафиксирован;
* NEXT_EI увеличен, но операция нигде не существует.

До journal commit возможен rollback.

После journal commit операция должна быть доведена recovery-механизмом.

Все изменения проходят только через Phase 1 Reliability Skeleton и `ApplyOperation`.

## СТРОКА ЗАКАЗА

До первого прихода строка заказа:

* A — № заказа;
* B — название;
* D — № счёта, если есть;
* E — артикул, если есть;
* H — заказанное количество;
* I — единица;
* L — поставщик;
* P — дата заказа;
* Q — ожидаемая дата;
* остальные поля по необходимости.

V ЕИ до фактического прихода пустая.

F до фактического прихода пустая или 0 согласно принятому отображению.

## ПЕРВЫЙ ФАКТИЧЕСКИЙ ПРИХОД

Первый приход позиции может использовать исходную строку заказа.

При проведении заполняются:

C — номер УПД/закрывающего документа, если есть;  
F — фактически принято;  
G — количество по документу;  
N — дата поступления;  
O — дата документа;  
U — место хранения;  
V — новый ЕИ;  
W — статус;  
X — текущий остаток этого конкретного ЕИ;  
Y — контроль.

H `Заказанное количество` остаётся исходным и никогда не переписывается фактом.

## НОВЫЙ ЕИ

Формат:

`ЕИ-00000001`

Источник следующего номера:

`NEXT_EI`.

Перед выдачей нового номера проверить, что:

* он не существует в `Наличие`;
* он не существует среди проведённых приходов;
* он не конфликтует с мигрированными старыми кодами;
* NEXT_EI не меньше фактического максимума.

Приход нового обычного товара всегда создаёт новый ЕИ.

Даже если название и артикул совпадают с уже существующим товаром, обычные товары не объединяются.

## `НАЛИЧИЕ`

При новом приходе в той же атомарной операции создаётся новая строка реестра ЕИ.

Записать минимум:

* ЕИ;
* название;
* артикул;
* базовую единицу;
* количество;
* место;
* категорию;
* статус;
* источник / № заказа при необходимости;
* служебные сведения, разрешённые архитектурой.

Плотная адресация:

`номер ЕИ → строка реестра`.

После первого прихода:

`Заказы.X = текущий остаток конкретного ЕИ`.

Это не общий остаток одинакового товара.

## ЧАСТИЧНЫЙ ПРИХОД

Пример:

заказано H = 100.

Первый УПД:

F = 40.

Статус позиции:

`Частично получено`.

Осталось получить:

60.

Второй приход создаёт новую строку фактического поступления той же позиции заказа.

В дополнительной строке:

* A — тот же № заказа;
* D — тот же № счёта;
* B/E/I/L и другие идентифицирующие данные позиции — копируются системой;
* C — новый документ;
* F — новый фактический приход;
* G — количество по новому документу;
* N/O — даты этого прихода;
* V — новый ЕИ;
* H — пустая.

Нельзя повторять H = 100 во второй строке.

## СВЯЗЬ ДОПОЛНИТЕЛЬНЫХ ПРИХОДОВ

Нельзя связывать строки только по:

`№ заказа + текст названия`.

Нужна служебная идентичность исходной позиции заказа вне неизменяемых колонок.

Использовать схему, совместимую с Phase 1/2:

* постоянный OrderLineID в служебной структуре;
* номер строки — только подсказка;
* перед использованием подсказка проверяется;
* после вставки/сдвига строк связь восстанавливается по ключам/отпечатку.

Опиши точную модель в отчёте.

## НЕСКОЛЬКО ПОЗИЦИЙ В ОДНОМ ЗАКАЗЕ

Один № заказа может содержать много разных товарных позиций.

Система должна различать позиции независимо.

Нельзя считать все строки одного `№ заказа` одной товарной позицией.

## НЕСКОЛЬКО УПД

Один счёт/заказ может иметь:

* один УПД;
* несколько УПД;
* частичные поставки в разные даты.

Каждое фактическое поступление обычного товара:

* отдельная строка;
* отдельный ЕИ;
* отдельная операция прихода.

## КОЛИЧЕСТВА

H — заказано.

G — по документу.

F — фактически принято.

Проверки:

* F > 0;
* G > 0, если документное количество указано;
* F/G проходят locale-independent parser;
* отрицательные, даты, экспоненты, неоднозначные записи запрещены.

Контроль:

* G = F → нормально;
* G > F → недостача;
* G < F → излишек.

Недостача/излишек не должны сами менять H.

## СТАТУСЫ

Для обычного заказа Phase 3 поддержать минимум:

* `Ожидается`;
* `Просрочено`;
* `Частично получено`;
* `Получено`;
* `Получено без документов`;
* `Отменено`;
* `Частично получено / остаток отменён`.

Статус должен вычисляться на уровне исходной позиции заказа с учётом всех связанных фактических приходов.

Дополнительные строки прихода могут иметь свой технический/визуальный статус, но источник бизнес-статуса позиции должен быть однозначен.

## ПРОСРОЧЕНО

`Просрочено` зависит от Q и текущей даты.

Нельзя делать тяжёлый пересчёт всего листа после каждой операции.

Разрешён подход:

* обновлять только открытые позиции;
* пересчитывать просрочку при открытии;
* отдельная кнопка обновления статусов.

Опиши выбранную модель.

## ПОЛУЧЕНО БЕЗ ДОКУМЕНТОВ

Если физический приход произошёл, но C/O не заполнены:

товар всё равно существует в `Наличие`;

ЕИ создаётся;

остаток доступен для выдачи;

статус показывает отсутствие документа.

Позднее документ можно добавить без повторного прихода и без создания нового ЕИ.

## ОТМЕНА ЗАКАЗА

До фактического прихода:

`Отменено`.

Никакой ЕИ не создаётся.

NEXT_EI не расходуется.

История заказа остаётся.

## ОТМЕНА ОСТАТКА

Если:

заказано 100;

получено 40;

оставшиеся 60 больше не будут поставлены,

действие:

`Отменить остаток`.

Статус:

`Частично получено / остаток отменён`.

H остаётся 100.

Факт остаётся 40.

История не удаляется.

## ИСПРАВЛЕНИЕ ПРИХОДА

Проведённый приход нельзя менять вручную.

Действие:

`Исправить`.

Рекомендуется одна составная операция:

`RECEIPT_FIX`.

Она должна:

* отменить старое влияние;
* проверить новое состояние;
* применить новое;
* сохранить тот же существующий ЕИ, если исправляется количество/документ/место и физическая партия остаётся той же;
* не выдавать новый ЕИ без необходимости.

Критическая проверка:

исправление количества прихода не может привести к:

`новый приход < уже выданное количество этого ЕИ`.

Если было принято 10, уже выдано 7:

исправить приход на 5 нельзя.

## УДАЛЕНИЕ ПРИХОДА

`Удалить` = сторно прихода.

Если по ЕИ уже есть выдачи или другие зависимые движения — удаление, создающее отрицательный результат, запрещается.

ЕИ после отмены не переиспользуется.

Его запись остаётся в реестре с соответствующим статусом.

Физическое удаление истории запрещено.

## МЕСТО ХРАНЕНИЯ

U обязательно для проведённого обычного прихода.

Один ЕИ имеет одно текущее место.

На этом этапе отдельное действие перемещения не реализовывать.

## АРТИКУЛ

Для обычного товара артикул может быть пустым.

Артикул обычного товара не является ключом объединения.

Не выполнять поиск «такой товар уже существует».

## ЦЕНА И СУММА

J `Цена` и K `Сумма` сохранить.

На Phase 3 не строить ценовую аналитику.

Не придумывать бухгалтерские правила.

Если цена есть:

проверить числовой формат.

Точную бизнес-формулу K не менять без существующего утверждённого правила.

Если в MASTER SPEC формула K ещё не определена — оставить K пользовательским/информационным полем и указать это в отчёте.

## АНТИДУБЛЬ

AB `Возможный дубль`.

Нужна лёгкая проверка через индекс/compound key.

Не сканировать весь лист.

Проверять минимум разумную комбинацию:

* поставщик;
* документ;
* артикул или нормализованное название;
* количество;
* дата.

Это только предупреждение.

AB не должно автоматически блокировать реальный приход без отдельного правила.

## ЗАЩИТА

После проведения фактического прихода защитить поля, влияющие на складской учёт.

Поля документов/комментария, которые безопасно менять без изменения движения, могут оставаться редактируемыми только если это не разрушает контрольную сумму операции.

Опиши точный набор закрытых колонок.
