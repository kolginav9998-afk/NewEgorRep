## СНАЧАЛА ИСПРАВИТЬ PROJECT MEMORY

В текущем `WMS_DECISIONS.md` отсутствуют D-011…D-024.

Это не новые решения. Они были утверждены ранее, но потерялись при переносе документов.

Если исторический файл с точным текстом доступен — восстановить текст из него.

Если его нет, использовать следующие канонические решения.

**D-011 — История получателя.** История показывает, что и когда выдавалось получателю и какие возвраты были зарегистрированы. Она не утверждает, что невозвращённый товар физически до сих пор находится у этого человека.

**D-012 — Получатели.** Люди, `Офис`, `Производство` и другие допустимые текстовые получатели являются значениями одного типа для истории выдач. Поддерживается справочник сокращений. Одно сокращение принадлежит одному получателю и должно быть уникальным.

**D-013 — Проведённые строки.** После проведения учётные ячейки защищаются. Ручная правка полей, влияющих на учёт, запрещена. Изменения выполняются через штатные команды WMS.

**D-014 — Ctrl+Z.** Учётная операция защищается от частичного отката через Undo. Исправления и удаление проводятся только командами WMS.

**D-015 — Внешний журнал.** Разрешён и обязателен append-only журнал рядом с WMS для восстановления проведённых, но ещё не сохранённых в ODS операций.

**D-016 — Резервные копии.** Разрешена отдельная папка backups. Базовая политика — одна копия рабочего дня плюс обязательные копии перед обновлением и миграцией.

**D-017 — Подстановки.** Разрешены лёгкие обработчики изменения нужных ячеек, если они не сканируют большие диапазоны, защищены от повторного входа и отключаются в Safe Mode.

**D-018 — Архив.** Архивируется тяжёлая история, но все ЕИ навсегда остаются в постоянном реестре. Архивный ЕИ может снова стать активным после возврата.

**D-019 — Отдельные инструменты.** Тяжёлые функции выполняются отдельными ODS-инструментами через read-only снимок основной WMS.

**D-020 — Ежедневный отчёт.** Нужен один ежедневный отчёт руководителю. WMS формирует черновик автоматически, после чего пользователь может вручную изменить итоговый текст.

**D-021 — Аналитика.** `WMS_ANALYTICS.ods` анализирует текущую историю и архивы, строит статистику, прогноз дефицита, рекомендации заказа и нагрузку. Тяжёлая аналитика не выполняется автоматически в рабочей WMS.

**D-022 — GitHub.** GitHub является долговременной памятью проекта. Исходники Basic хранятся текстом. Commit/push/PR/ветки выполняются только в явно разрешённом объёме.

**D-023 — Риск-прототипы.** До основной разработки обязательны P1–P4: идентичность строк, производительность, crash recovery, persist/reopen/cross-platform.

**D-024 — Завершение интервью.** Основное бизнес-интервью завершено. Незначительные правила уточняются перед соответствующим модулем и не должны бесконечно задерживать разработку.

Не перенумеровывать D-025…D-038.

# ЛИСТ `Выдачи`

Структура строго неизменяема:

A №  
B № документа выдачи  
C Наименование  
D Артикул  
E Количество  
F Количество в %  
G Единица измерения  
H Дата выдачи  
I Кому выдано  
J Место хранения  
K Категория  
L Внутренний код  
M Вернул  
N Вернул в %  
O Комментарий  
P Остаток до выдачи  
Q Остаток после выдачи  
R Контроль

Нельзя добавлять служебные колонки.

`L Внутренний код` = ЕИ.

`A №` выдаёт только WMS при проведении.

Пустой A означает, что строка ещё не проведена.

M/N пока legacy. Phase 2 их не изменяет.

# ИСТОЧНИК ТОВАРА

Для Phase 2 использовать постоянный реестр `Наличие`.

Одна строка = один ЕИ.

Плотная адресация:

`номер ЕИ → строка реестра`.

Никакого поиска похожего названия.

Никакого полного EnumerableMap по всем ЕИ.

В production-книге реестр может быть пустым.

В test build создать синтетические ЕИ для сценариев тестирования.

Пользователь может в L вводить, например:

`123`

`00000123`

`ЕИ-123`

`ЕИ-00000123`

`EI-123`

`ЕИ-00000123`

J — Место хранения  
K — Категория  
P — текущий остаток

L приводится к каноническому виду.

Если ЕИ неизвестен:

R = понятная ошибка;

проведение запрещено.

Никаких MessageBox при обычной успешной подстановке.

# ИСПРАВИТЬ

Реализовать действие `Исправить` для проведённой выдачи.

Не разрешать просто разблокировать строку и переписать значения.

Сценарий:

старое движение сторнируется через тот же Reliability Skeleton;

проверяется новый ЕИ/количество/получатель;

применяется новое движение;

остаток становится корректным;

история операции сохраняется в journal;

строка снова защищается.

Если новое количество невозможно по текущему складу — исправление блокируется без повреждения старого состояния.

Crash между сторно и новым движением не должен оставлять систему в неопределённом состоянии.

Если безопаснее архитектурно представить исправление как одну составную операцию — использовать этот путь и описать его.

---

# УДАЛИТЬ

`Удалить` для проведённой выдачи означает безопасное сторно.

Физически нельзя просто удалить влияние строки на склад.

После удаления:

остаток возвращается;

journal содержит сторно;

исходный номер A не переиспользуется;

история сохраняется.

Пользовательская строка либо очищается безопасным способом, либо получает однозначный статус отмены согласно выбранной реализации.

Не использовать скрытие строки как способ удаления.
