M7 PRIME — LEGACY TRANSFER WIZARD: ОДИН ФАЙЛ ДЛЯ ПОЛНОГО ПЕРЕНОСА СТАРОЙ ТАБЛИЦЫ В WMS 0.7
База: последний зелёный release `WMS_RELEASE_0.7.0`, commit `e65f606`, ветка `claude/festive-lamport-l4f8f1`.
Цель этапа — сделать отдельный автономный инструмент `WMS_LEGACY_TRANSFER.ods`, с которым пользователь сможет перенести старую рабочую таблицу в новую WMS одним массовым действием, без ручного переноса сотен строк и без передачи данных разработчику.
Главный пользовательский сценарий должен быть максимально простым:
1. Открываю старую таблицу.
2. Выделяю весь лист `Заказы` A:AB.
3. Копирую.
4. Вставляю одним блоком в `WMS_LEGACY_TRANSFER.ods`.
5. Нажимаю `ПРОВЕРИТЬ`.
6. Если всё нормально — `СОЗДАТЬ НОВУЮ WMS`.
7. Инструмент сам строит полноценную рабочую WMS 0.7 с сохранёнными заказами, статусами, EI и остатками.
Пользователь не должен вручную готовить CSV, переименовывать сотни колонок, чистить статусы, удалять формулы или по одной переносить позиции.
1. Отдельный инструмент
Создать:
`WMS_LEGACY_TRANSFER.ods`
Он не должен быть частью боевой WMS и не должен менять исходную старую книгу.
Основные пользовательские листы:
`1_Вставить_Заказы`
Сюда пользователь вставляет весь старый диапазон `Заказы` A:AB одним Ctrl+V.
Структура старого листа соответствует прежней/текущей логике `Заказы`:
A № позиции внутри заказа
B Полное наименование товара
C Номер документа
D Номер счёта
E Артикул
F Фактическое количество
G Количество по документу
H Заказанное количество
I Единица измерения
J Цена
K Сумма
L Площадка / Поставщик
M Продавец
N Дата поступления
O Дата документа
P Дата заказа
Q Ожидаемая дата поступления
R Покупатель
S Категория
T Кому назначено
U Место хранения
V Внутренний код / EI
W Статус
X Наличие
Y Контроль
Z Комментарий
AA Срок поставки, дней
AB Возможный дубль
Инструмент должен выдерживать вставку с формулами, вычисленными статусами и служебными значениями старой таблицы.
Внутри staging обязательно работать с вычисленными значениями, а не переносить в новую WMS старые формулы, ссылки, макросы или внешние зависимости.
Если вставленная формула ссылается на старую книгу, Transfer должен зафиксировать её текущее вычисленное значение как source value и не переносить формулу в PROD.
2. Группировка заказов
Критически важно правильно понять старую систему.
В колонке A не номер заказа, а номер позиции внутри заказа.
Последовательность:
`1,2,3,4,5,1,2,3,1,2,3,4`
означает три заказа.
Каждая новая исходная строка с A=`1` начинает следующий заказ.
Поэтому Transfer должен восстановить внутренние OrderID/OrderLineID новой WMS именно из этих блоков.
Дочерние строки/дополнительные поступления нужно распознавать отдельно и привязывать к родительской позиции, если они присутствуют в старом файле.
После переноса новая WMS должна визуально сохранить ту же структуру заказов, включая горизонтальное разделение между блоками.
3. Что переносить
Переносить максимально всё полезное содержимое A:AB:

* структуру заказов;
* наименование;
* артикул;
* заказанное количество;
* фактически полученное;
* количество по документу;
* единицу;
* цену;
* сумму;
* поставщика;
* продавца;
* счёт;
* УПД/документ;
* даты;
* ожидаемую дату;
* покупателя;
* категорию;
* назначение;
* место;
* комментарий;
* существующий EI;
* текущее наличие;
* исходный статус;
* исходный контроль;
* срок поставки;
* признак возможного дубля.

Не переносить старые стили/макросы/кнопки как архитектуру. Переносить данные и смысл в новую чистую WMS 0.7.
4. Статусы
Старый статус W сохранить как:
`LegacyStatus`
для сверки.
Но итоговый рабочий статус новой WMS должен быть пересчитан новым движком, а не слепо скопирован.
Поддержать минимум:

* Ожидается;
* Просрочено;
* Частично получено;
* Частично получено / просрочено;
* Получено;
* Получено без документов;
* Отменено;
* Частично получено / остаток отменён.

В отчёте показать:
`Старый статус → Новый рассчитанный статус`
Расхождение не всегда является ошибкой, но должно быть явно показано.
Критическое противоречие должно блокировать автоматический promote.
5. EI
Существующие внутренние коды сохранять обязательно.
Например:
`ЕИ-00000427`
после переноса остаётся:
`ЕИ-00000427`.
Поддерживать старые формы:
`427`, `00000427`, `ЕИ-427`, `EI-427`
и приводить к каноническому виду.
Никогда не перенумеровывать физически существующие EI.
После импорта:
`NEXT_EI > max(всех перенесённых EI)`.
Дубли EI с несовместимыми товарами = BLOCKER.
Один старый EI в нескольких строках допустим только если это логически один и тот же объект/партия и новая модель это допускает.
6. Текущие остатки
В старой таблице колонка X `Наличие` может содержать текущий остаток.
Для уже полученного EI нельзя считать F “Фактическое количество” текущим остатком, потому что после прихода могли быть старые выдачи.
Приоритет определения стартового остатка:

1. корректное значение X `Наличие`, если оно достоверно и относится к данной позиции;
2. дополнительный лист старого `Наличие/Остаток`, если пользователь его вставил в необязательный staging;
3. вычисление из старых движений, если доступны старые `Выдачи/Возвраты`;
4. иначе строка получает `Требуется проверить остаток`.

Никогда не создавать фиктивный остаток из F без явного правила.
Добавить необязательные листы:
`1B_Вставить_Наличие`
`1C_Вставить_Выдачи`
`1D_Вставить_Возвраты`
Но основной режим должен работать только с `Заказы A:AB`, если в нём достаточно данных.
Пользователь не обязан заполнять дополнительные листы.
7. Открытые заказы
Это ключевое требование.
После переноса должны сохраниться не только остатки, но и незаконченные заказы.
Например:
старая строка:
`Заказано 100 / получено 40 / осталось получить 60`
должна стать полноценной позицией новой WMS:
`получено 40 / ожидается 60`.
После миграции пользователь должен иметь возможность нажать обычное:
`Ещё поступление`
и продолжить старый заказ уже новым движком.
Не создавать мёртвый текст.
То же для:

* полностью ожидаемых;
* частично полученных;
* просроченных;
* заказов без документов;
* частично закрытых;
* отменённых.

8. Построение внутренней архитектуры
Нельзя просто вставить A:AB в `WMS_PROD`.
Transfer должен построить корректное внутреннее состояние новой версии:

* `Заказы`;
* `_ORD`;
* `_RCV`;
* `Наличие`;
* индексы;
* внутренние OrderID / OrderLineID;
* связи receipt → order;
* EI registry;
* счётчики `_SYS`;
* индексы деталей;
* миграционную историю;
* необходимые стартовые journal records.

После переноса все старые позиции должны вести себя так, будто новая WMS всегда знала о них.
Обычные функции:

* `Ещё поступление`;
* `Выдача`;
* `Возврат`;
* `MOVE`;
* `WRITE_OFF`;
* `INV_ADJ`;
* Search;
* Analytics;
* Doctor

должны работать на перенесённых EI без специального режима.
9. Детали
Соблюдать правило новой WMS:
один уникальный артикул детали → один EI.
При импорте:

* одинаковый нормализованный артикул + один EI → нормально;
* одинаковый артикул + два EI → blocker;
* деталь без артикула → `Требует разбора`;
* повторные приходы детали должны реконструироваться как пополнения существующего EI, если это можно определить однозначно.

Использовать ту же нормализацию артикула, что в WMS 0.7.
